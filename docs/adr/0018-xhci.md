# ADR-0018: xHCI — a second USB host controller, sharing only the parsers

## Status

Accepted and verified for V0.8 (`xhci-hid-bios`).

## Context

V0.6 brought up UHCI and read HID input through it. xHCI is not a newer UHCI;
it is a different machine. UHCI has the driver build transfer descriptors into
a frame list that the controller walks on a fixed schedule. xHCI is ring-based
and command-driven: the driver posts TRBs to rings, rings a doorbell, and every
result — a command completion, a transfer completion, a port change — appears
on an event ring the controller owns.

## Decision

**Add a second driver rather than generalise the first.** The two controllers
share `kernel_core::usb` — descriptor parsing, HID report decoding — and
nothing else. An abstraction over "USB host controller" written from two
examples, one of which is a 1996 design, would be a layer that fits neither.
What *is* shared is the part that is genuinely common: the bytes a USB device
sends about itself.

**Three rings, one shape.** A command ring for controller-level operations
(Enable Slot, Address Device, Configure Endpoint), a transfer ring per
endpoint, and the event ring the driver drains. Every ring ends in a Link TRB
with Toggle Cycle, so the producer cycle bit flips on each lap — without it the
controller stops the moment it wraps, which presents as "enumeration hangs
after sixteen operations".

**Polled, like every other driver here.** The event ring is drained against a
real-time deadline, not from an interrupt handler (ADR-0015, ADR-0017). A
missing completion is therefore a timeout with a message naming the operation,
never a hang.

**The device is configured as well as the controller.** Configure Endpoint
tells the *controller* about the interrupt endpoint; the *device* still needs
`SET_CONFIGURATION` to leave the Address state and `SET_PROTOCOL(boot)` to
report in the layout the HID boot protocol specifies. Omitting either leaves a
perfectly configured endpoint that never sends anything — a failure that looks
like broken hardware. `SET_PROTOCOL` is allowed to stall: a device with no
alternative protocol has nothing to switch away from.

**Input is tagged with its source.** A report delivered through xHCI is logged
`src=xhci`, as the UHCI path logs `src=usb`. A test that could not say which
controller delivered a keystroke would prove nothing about either.

## Consequences

Both controllers can be present; the device model binds whichever the machine
has. The `xhciwait` command is separate from `usbwait` for the same reason the
tags differ.

## Limitations

One device, one interrupt endpoint, one slot. No hubs, no bulk or isochronous
transfers, no USB3 streams, no runtime device attach or detach — a device
plugged in after boot is not noticed. Scratchpad buffers are allocated when the
controller asks for them but the driver has no other use for them. Interrupts
are not used: MSI-X on the xHCI controller is left unarmed, and the MSI-X
delivery proof rides on the NVMe controller instead (ADR-0017).

## Evidence

`artifacts/qemu/xhci-hid-bios.result.json`. Controller reset and ring setup
(`xhci ready caplength=64 slots=64 ports=8 context_size=32`), Enable Slot and
Address Device, two control IN transfers yielding the device descriptor
(`vendor=0x0627`) and the configuration descriptor, the HID interrupt endpoint
located at `iface=0 endpoint=0x81`, and finally a real injected keypress
arriving over an interrupt transfer: `XHCI-HID-REPORT bytes=8 … ascii=g` and
`[ITISYOU:INPUT] key=g src=xhci`.
